# Data and credential boundaries

Backup roots must be dedicated, trusted local filesystems supporting flock, atomic rename and fsync. A configured Docker backup root must be an actual mount. This cannot prove that the host mounted the intended NAS device: operators must verify the host mount before starting the stack. Symlinks and special files in the data tree are rejected. Do not allow concurrent untrusted filesystem writers. SMB/NFS consistency is not guaranteed.

Git uses argument lists, disabled prompts, an isolated environment, disabled system/global config, hooks and fsmonitor, TLS verification, no HTTP redirects, and HTTPS-only production transport. Secret values are provided only in a child-scoped askpass environment, never arguments or remote URLs. Child environments can be inspected by the same OS identity/root; keep host access restricted. Self-managed HTTPS hosts are supported, so network reachability is controlled by the trusted stack configuration and container network policy. Local Git transport is enabled only by test fixtures, not by a product setting.

Git stderr is never forwarded into logs or persistent error messages. The application exposes fixed internal error codes. SAST blocks medium/high findings; low-severity B404/B603 notices describe the required, reviewed shell-free Git subprocess boundary. No arbitrary configured command can reach that boundary.

The central `data.json` is written before mutating Git operations, with temporary-file fsync, atomic replace and directory fsync. Repository metadata precedes journal completion. A durable Git-completion marker permits idempotent replay after a crash, without double-counted successes. No valid mirror is deleted or overwritten with a fresh clone. Ordinary updates fetch directly with atomic reference updates and prune; this is not a transaction over the entire object database.

On startup, only interrupted/suspect repositories receive a local `fsck --full`. Dangling objects alone are not corruption. A partial clone with durable successful completion plus a fresh valid integrity check can be promoted atomically. A proven interrupted initial clone is moved into the single `quarantine/initial-clone` slot under its repository directory, using durable metadata and a central journal entry before rename. Its contents remain preserved and count towards both global and repository budgets. Boot does not clone: a fresh attempt waits for the next regular cron run. Per-repository operation ownership survives the next source overwriting the central active-operation slot. A second partial when the slot is occupied, an unowned partial, an excluded source, or conflicting/missing quarantine contents sets the persistent `backup.manual_attention_required` reason and blocks further downloads. No automatic deletion or unbounded quarantine rotation occurs. Missing/corrupt journals or metadata require manual inventory and fail closed. Schema 1 is the only supported schema; future schemas are rejected, never reset.

Repair re-fetches the existing ref-tip object IDs with no destination refspec and disabled implicit ref mapping. It preserves backup refs and verifies integrity again. At most three actual failed attempts occur for one corruption incident; success resets the incident counter. Stops and capacity aborts leave an interrupted journal and do not consume the failure budget. If capacity prevents starting a repair, `backup.repair_deferred` preserves the pause reason so the next regular run can re-evaluate it; this does not consume an attempt or require a service restart. Completed repair operation IDs make metadata/error counters idempotent after a crash. Git references are preserved even when a repair is interrupted. Repair requires an included source, enabled repair and available storage. Excluded repositories receive no remote downloads. Objects no longer available on the source, invalid refs/config or irrecoverable pack damage can remain `repair_failed`; an administrator must investigate with preserved data. This is not a general Git-repair service.

SIGTERM/SIGINT prevent new Git work, terminate the process group, escalate to SIGKILL after five seconds if necessary, reap children and preserve interruption state. A fatal persistence error stops the worker/service and leaves its journal recoverable. SIGKILL cannot perform cleanup; container init and restart reconciliation handle that boundary.

For `manual_attention_required`, stop the service before touching backup data. Inspect `metadaten.json` and the journal and preserve both the partial and any existing quarantine. Archive the partial by a non-overwriting move into an operator-chosen unique directory under `<backup-root>/operator-archive/` (outside `manual/`); keep it until separately reviewed. An occupied quarantine slot can likewise be archived explicitly, never overwritten or deleted. Local `git fsck --full` and an offline `git clone --no-hardlinks` from an existing mirror may aid diagnosis, but healthy structure alone does not prove an interrupted initial clone was complete. Never replace `repository.git`, delete the journal, or edit success timestamps to bypass this state. On restart, once the partial conflict is resolved, recovery clears the attention field and waits for a future cron run; archives still count towards the global budget. If a pending quarantine reports missing content, restore that recorded slot from the preserved archive before restarting; otherwise keep the case blocked for manual data recovery.

Scheduler overlap events and worker journal transitions use the same serialized read-modify-write transaction, including fsync. Each observed overlap is persisted immediately, even while Git is running. A failed state write stops the service; it does not authorize starting an unjournaled Git operation. Inventory sizes are point-in-time measurements before and after operations, with measurement timestamps; they are not hard quotas.
